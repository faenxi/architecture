# Лабораторна робота №2

## Тема

Застосування принципів SOLID у системі кошика інтернет-магазину.

## Мета

Розширити систему з ЛР1 та продемонструвати SRP, OCP, LSP, ISP і DIP.

## Застосування SOLID

### 1. Single Responsibility Principle

- `ShoppingCart` відповідає лише за стан і розрахунки кошика;
- `PercentageDiscountPolicy` - лише за розрахунок відсоткової знижки;
- `CheckoutService` - за координацію оформлення;
- `InMemoryOrderRepository` - за збереження;
- `ConsoleCartView` - за консольний вивід.

Кожен клас має одну основну причину для зміни.

### 2. Open/Closed Principle

`CheckoutService` працює з `DiscountPolicy`. Нову знижку можна додати окремим
класом, який реалізує цей інтерфейс, не редагуючи сервіс оформлення.

### 3. Liskov Substitution Principle

`NoDiscountPolicy` і `PercentageDiscountPolicy` приймають однакові допустимі
аргументи, повертають невід'ємну суму та не посилюють передумови контракту.
Метод демонстрації працює з обома без перевірки їхнього конкретного типу.

### 4. Interface Segregation Principle

Інтерфейс кошика розділено на `CartCommands` і `CartQueries`: консольному
поданню потрібні тільки запити читання. Зовнішні можливості також розділено на
`PaymentProcessor` і `ReceiptSender`, тому клієнти не залежать від зайвих методів.

### 5. Dependency Inversion Principle

Високорівневий `CheckoutService` залежить від абстракцій `DiscountPolicy`,
`PaymentProcessor`, `OrderRepository`, `ReceiptSender`. Конкретні реалізації
передаються через конструктор у точці запуску програми.

## Перевірка

Запуск `./run.sh lab2` показує взаємозамінність двох політик і оформлення зі
залежностями, переданими через інтерфейси. Запуск `./run.sh test` автоматично
перевіряє розрахунок кошика, LSP-контракт політик, оплату, збереження та
очищення кошика.

## Висновок

Після розширення система зберегла просту структуру, але стала придатною до
додавання нових знижок, платіжних систем, способів надсилання чеків і сховищ
без зміни основної бізнес-логіки.
